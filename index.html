基础-1 — CE 入门 — 内存搜索与修改

✅ 已完成   Cheat Engine 7.x

Cheat Engine 基础操作

Cheat Engine (CE) 是最常用的游戏内存修改工具。核心功能：附加进程 → 搜索数值 → 筛选变化 → 锁定修改。

精确数值搜索

1. 打开 CE → 附加目标进程
2. 输入当前数值（如 HP=100）→ 首次搜索
3. 游戏中改变数值（掉血到 80）→ 再次搜索 80
4. 反复筛选直到只剩几个地址
5. 双击地址加入列表，修改数值验证

数据类型

类型字节范围典型用途
Byte10-255子弹数、命数
2 Bytes20-65535小数值
4 Bytes40-4.29B血量、金币（最常用）
Float4±3.4E38坐标、速度
8 Bytes8极大大型数值、Double

模糊搜索

不知道具体数值时用：未知初始值 → 增大/减小 → 反复筛选。适合搜索血条百分比、计时器等。

复习锚点

数值搜索找到的是“当前值所在地址”，不自动等于永久地址。先用数值变化缩小候选，再用实际修改确认它确实影响目标状态。

验证与证据

看到什么说明什么
数值变化后候选地址持续减少筛选条件正在排除无关内存
修改候选值后目标状态立即变化该地址与目标数据存在直接关系
重启后地址失效它很可能是动态分配地址，需要继续追踪指针链

常见误区与排查

候选太多时，不要盲目修改；先在目标中制造明确的增减变化。数值搜不到时，先怀疑数据类型、显示值与真实值不同，或数值被拆分/加密，而不是立刻认定工具失效。

关联与防御视角

本课为指针扫描建立入口。防御侧关心的不是“有人找到一个地址”，而是进程外部是否反复读取、写入或锁定敏感数据。

版本与资料

结论与目标程序版本、数据类型和内存布局相关。资料方向：Cheat Engine 官方教程；Microsoft Learn 的进程虚拟内存概念。

基础-2 — 指针扫描 — 基址与多级偏移

✅ 已完成   Cheat Engine 指针扫描

为什么需要指针扫描

重启游戏后，之前找到的地址会失效——因为数据在内存中的位置每次都在变（ASLR、动态分配）。但基址不变，只需要找到从基址到数据的指针链。

CE 指针扫描流程

1. 找到血量的动态地址
2. 右键 → 「找出是什么访问了这个地址」
3. 游戏中让血量变化，CE 捕获到访问指令
4. 查看汇编：mov eax, [rcx+0x58] → 偏移 = 0x58
5. 记录 rcx 的值，继续往上追
6. 最终找到：TestGame.exe+0x1F4D8 → +0x0 → +0x58 = 血量

多级指针结构

[TestGame.exe + 0x1F4D8]  ← 基址（不变）
       ↓
    [g_pPlayer]           ← 第 1 级指针
       ↓ +0x58
    [HP = 100]             ← 最终数据

静态指针 vs 动态指针

类型重启后怎么找
动态地址❌ 失效每次重新搜
静态指针（基址+偏移）✅ 永久有效指针扫描 + 人工验证

复习锚点

动态地址会变，能跨重启复现的是“模块基址 + 指针解引用 + 偏移”的关系。偏移不是地址本身，而是对象内部字段相对某个指针的距离。

验证与证据

检查合格现象
重启目标程序原动态地址改变，但同一条指针链仍能到达正确数据
查看访问指令能把类似 [rcx+offset] 拆成对象指针与字段偏移
更换一次游戏状态指针链读取的值随对象状态同步变化

常见误区与排查

不要把寄存器当前值当成永久基址；寄存器只是某次执行时的临时上下文。指针链重启失效时，先检查模块版本、对象生命周期和中间层是否选错。

关联与防御视角

本课把“数据地址”推进到“对象结构”。后续逆向看到 [rcx+0x58] 时，应自然想到它可能是对象字段访问。防御侧则更关注异常读写是否围绕稳定模块偏移和敏感对象展开。

版本与资料

ASLR 会改变模块加载基址，程序更新也可能改变偏移。资料方向：Microsoft Learn 的地址空间布局与 Windows 调试文档。

基础-3 — LoadLibrary DLL 注入 — 第一个注入器

✅ 已完成   Visual Studio 2026, C++

什么是 DLL 注入

把你自己写的 DLL 塞进目标进程的地址空间，让它在目标进程内部执行代码。注入后你的 DLL 就像游戏自己的一部分——可以直接读写游戏内存。

LoadLibrary 注入原理（最经典的注入方式）

1. OpenProcess — 打开目标进程
2. VirtualAllocEx — 在目标进程里分配内存
3. WriteProcessMemory — 把 DLL 路径字符串写进去
4. CreateRemoteThread — 让目标进程调用 LoadLibraryA(你的DLL路径)
5. Windows 加载器加载你的 DLL → DllMain 执行

注入器核心代码

HANDLE hProc = OpenProcess(PROCESS_ALL_ACCESS, FALSE, pid);
LPVOID pRemote = VirtualAllocEx(hProc, NULL, 4096,
    MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);
WriteProcessMemory(hProc, pRemote, dllPath,
    strlen(dllPath) + 1, NULL);
LPTHREAD_START_ROUTINE pLoadLibrary =
    (LPTHREAD_START_ROUTINE)GetProcAddress(
    GetModuleHandleA("kernel32.dll"), "LoadLibraryA");
CreateRemoteThread(hProc, NULL, 0, pLoadLibrary,
    pRemote, 0, NULL);

为什么注入后不需要 OpenProcess

注入后你的 DLL 跑在游戏进程内部，和游戏共享同一个虚拟地址空间。一个普通指针就能直接读写游戏的内存——不需要跨进程 API。

复习锚点

LoadLibrary 注入的核心不是“把 DLL 文件复制进去”，而是让目标进程里的 Windows Loader 正常加载该 DLL。成功后 DLL 与目标共享同一虚拟地址空间。

验证与证据

检查点应看到的证据
模块视图目标进程模块列表出现预期 DLL
线程与入口能关联到远程线程与系统加载流程
DLL 行为DllMain 或后续工作线程产生预期、可观察的实验结果

常见误区与排查

路径编码错误会导致加载失败，含中文路径优先使用宽字符版本。位数必须匹配：x64 目标配 x64 DLL；不要在 DllMain 内做长时间工作或依赖复杂初始化。

关联与防御视角

它是后续 Manual Map 的参照物：前者把 Loader 工作交给系统，后者自己承担。防御侧可关联跨进程句柄、写入 DLL 路径、远程线程和新增模块这条行为链。

版本与资料

结论受进程架构、权限和 Windows Loader 行为影响。资料方向：Microsoft Learn 的 Dynamic-Link Library Best Practices 与 LoadLibrary 文档。

PE 签名

50 45 00 00 = "PE\0\0"。从「格式选择器」退化成了「强制校验位」。

COFF Header — 20 字节

偏移大小字段含义实测

0xFE2BNumberOfSections有几个节0A → 10

PE 位数判断（三层）

层字段问题答案
1PE 签名是 PE 格式？PE\0\0 = 是
2Machinex86/x64？0x8664 = x64
3MagicPE32/PE32+？0x020B = PE32+

复习锚点

PE 解析的第一条链是：MZ → e_lfanew → PE\0\0 → COFF → Optional Header → 节表。不要靠固定偏移猜结构，始终让前一个字段指向下一个结构。

已验证结论与调试证据

用 HxD 按偏移验证 MZ、e_lfanew、PE 签名、Machine 和 Magic。Machine 回答“目标机器架构”，Magic 回答“PE32 还是 PE32+”，两者不是同一个问题。

常见误区与排查

e_lfanew 是文件偏移，不是内存 RVA。看到 0x8664 不能跳过 Magic 判断；分析损坏样本时，应先检查每次跳转是否仍落在文件边界内。

关联与防御视角

Day 2 的节表、Day 3 的导入表和 Day 4 的重定位都从这里继续。分析者和防御工具都应先验证头部一致性，避免把伪造或截断数据当作正常 PE。

版本与资料

x86/x64 的 Optional Header 结构不同。资料方向：Microsoft 的 PE/COFF Specification。

节表结构（40 字节）

偏移大小字段含义
+0x008BName节名

核心概念

PointerToRawData = 文件地址，VirtualAddress = RVA。文件和内存是两个坐标系。

FileAlignment vs SectionAlignment

参数值含义
FileAlignment0x200文件对齐
SectionAlignment0x1000内存对齐（页）

常见节

节名作用为什么重要
.text代码Hook 改这里
.rdata只读数据导入/导出表
.data全局变量CE 搜的值在这
.reloc重定位ASLR 修正

复习锚点

文件偏移、RVA、VA 是三套坐标。节表负责把“文件里哪一段字节”对应到“加载后内存里的哪一段区域”。

已验证结论与调试证据

用 e_lfanew + 0x18 + SizeOfOptionalHeader 定位节表，再以每项 40 字节遍历。用 PointerToRawData 找文件内容，用 VirtualAddress 判断其加载后的 RVA。

常见误区与排查

不要把 SizeOfRawData 与 VirtualSize 当成相同概念；前者描述文件，后者描述内存。遇到地址换算错误时，先写清当前值属于哪套坐标，再决定是否加 ImageBase 或减去节的 RVA。

关联与防御视角

Manual Map 必须按节复制并建立正确内存布局；IAT Hook 也依赖对 .rdata 等区域的正确判断。防御侧可把不合理的节属性、重叠布局或可执行可写节作为可疑证据之一。

版本与资料

对齐值由样本的 Optional Header 决定，不能硬编码。资料方向：Microsoft 的 PE/COFF Specification。

IAT Hook 原理

程序代码不变，IAT 槽位被调包——把 IAT 里的函数地址替换成你的 Hook 地址。作弊场景：Hook Present 画透视。

复习锚点

导入表记录“我需要谁的函数”，IAT 是 Loader 最终填入“实际函数地址”的位置。程序通常通过 IAT 间接调用外部 API。

已验证结论与调试证据

沿 DataDirectory[Import] 找到 IMAGE_IMPORT_DESCRIPTOR，再分别观察 DLL 名、INT 与 IAT。加载前后最关键的变化是：IAT 槽位从名称/序号信息变为可调用地址。

常见误区与排查

INT 与 IAT 不是重复表；IAT 会被 Loader 改写。没有看到某个 API 的 IAT 并不证明程序没有使用它，程序也可能通过 GetProcAddress 动态解析。

关联与防御视角

重定位表

ASLR 下 DLL 基址变了，里头的绝对地址全错了。重定位表是「需修正的地址清单」，每条 RVA 加 delta。Dll1.dll 有 3 块、28 个条目。

进程地址空间

为什么 DLL 注入后无需 OpenProcess？ 注入后 DLL 跑在游戏进程内部，共享同一虚拟地址空间——一个普通指针就能直接读写。

注入前：你的进程 →[OpenProcess+WPM]→ 游戏进程
注入后：[游戏] [你的DLL] → 指针直接访问

复习锚点

导出表是模块“能提供什么”，导入表是模块“需要什么”，重定位表是 ASLR 后“哪些绝对地址要修正”。三者一起解释了模块如何被定位、互相连接并运行。

已验证结论与调试证据

导出函数可通过名称或序号定位；重定位时比较首选 ImageBase 与实际加载基址，差值就是要应用的 delta。注入 DLL 后，普通指针能直接访问目标数据，是因为代码已在目标进程自己的虚拟地址空间中执行。

常见误区与排查

RVA 不是绝对地址；VA 通常需要 ImageBase + RVA。ASLR 下不能假设 DLL 永远装在首选基址；若重定位目录缺失或处理错误，映射后的绝对地址会失效。

版本与资料

什么是 Shellcode

一段裸字节码，没有 PE 加载器、没有 CRT、没有导入表。必须自己从 PEB 找到 kernel32，自己解析导出表，自己动态拿函数地址。位置无关代码 (PIC)，shellcode 被放到任意内存地址都能正确执行。

x64 PEB 走法

GS:[0x60]         → TEB → PEB
PEB + 0x18       → PEB_LDR_DATA
LDR + 0x20       → InMemoryOrderModuleList
[rax]            → 1st: exe (skip)
[rax]            → 2nd: ntdll (skip)
[rax]            → 3rd: kernel32  → InMemoryOrderLinks
[rax + 0x20]     → kernel32.dll base (Win10 x64)

Shellcode 执行流程

1. PEB walk → kernel32.dll base
2. Parse export table → find "GetProcAddress" by name
3. GetProcAddress(kernel32, "LoadLibraryA")
4. LoadLibraryA("user32.dll")
5. GetProcAddress(user32, "MessageBoxA")
6. MessageBoxA(NULL, "Hello from shellcode!", "Shellcode", MB_OK)

主动注入 vs 系统被动注入

Day 5（手动映射）和 Day 6（Shellcode）都是主动注入——你自己调 OpenProcess、VirtualAllocEx、CreateRemoteThread 把代码塞进目标进程。

Day 7 是系统被动注入——你只调用一个合法的 Win32 API 注册钩子，系统在目标进程取消息时自动把你的 DLL 拉进去。

SetWindowsHookEx 工作流程

1. HookSetter.exe 调用 SetWindowsHookExW(WH_GETMESSAGE, GetMsgProc, hDll, 0)

   → 系统自动加载 HookDll.dll
   → 系统调用 GetMsgProc(nCode, wParam, lParam)
   → 末尾必须调用 CallNextHookEx，传给下一个钩子

关键：不碰目标进程。没调 OpenProcess，没调 VirtualAllocEx，没调 CreateRemoteThread。全是系统自己的正常行为。

APC = Asynchronous Procedure Call

往别人线程里排队塞一个函数调用。不创建新线程，复用已有线程执行代码。类比：CreateRemoteThread = 闯进去开一桌饭，QueueUserAPC = 留张便签等他闲下来自己看。

Day 9 — 注入体系总结

✅ 已完成   阶段性复盘：六种注入方式的统一模型

这一课真正要记住什么

不要把注入只记成六个名字。分析任何一种方式时，都先回答：代码在哪里、怎么进入目标进程、由谁执行、谁负责加载细节、会留下什么证据。

统一分析五问

问题要看的东西
代码载体是什么？DLL、完整 PE 镜像、Shellcode，还是跳板代码
内存从哪里来？系统正常加载、私有内存页，还是已存在模块中的位置
执行入口是谁？新线程、目标已有线程、GUI 消息回调、APC 回调
Loader 行为谁负责？Windows Loader，还是注入方自己处理导入、重定位、TLS 等细节
防御方能看到什么？模块、线程入口、可执行私有内存、上下文变化与跨进程行为链

六种方式对比

LoadLibraryDLL 路径新建远程线程调用系统 Loader流程正规、稳定；模块列表和加载痕迹明显
Manual Map完整 PE 镜像远程线程或映射器入口自己模拟 Loader；导入、重定位、TLS 漏一项都可能失败
Shellcode原始机器码新线程或其他执行入口无标准模块外形；调用约定、寄存器、栈对齐很关键

稳定、痕迹与控制权

越借助系统的正规流程，系统替你维护的秩序越多，所以通常越稳定；代价是模块、路径、线程和 Loader 行为更容易被观察到。越是自己控制执行链，就越要自己承担这些秩序：模块装载、内存权限、调用栈、寄存器和恢复现场。它不等于完全绕过系统，而是系统只提供基础能力，不再替你保证高级流程正确。

借系统流程：系统 Loader / 消息回调 / APC 机制

自己控制流程：私有可执行内存 / 自行处理 PE / 改写已有线程上下文

稳定性来自系统维护秩序；风险来自自己接管秩序。

线程劫持的原理

线程劫持的本质是临时改写一个已有线程的下一条执行位置：保存原始 RIP/EIP 与必要现场 → 让线程短暂进入 payload → 恢复现场并回到原始 RIP/EIP。如果没有保存原始位置，payload 结束后线程不知道该回哪里，原执行流会被截断。

它容易崩，是因为线程暂停时可能正在持锁、依赖寄存器中的值、使用栈上的局部数据，或正处于 Loader、GUI、同步等敏感逻辑。新建线程像给任务单独开一张干净的桌子；线程劫持则是在别人正在工作的桌面上临时插手。

反作弊：从证据反推注入家族

防御方不必一开始就准确叫出攻击技术名。更实用的顺序是：先建立可信的模块与内存边界 → 发现异常行为链 → 将证据映射到可能的注入家族 → 再做针对性验证。

Day 10 — 注入检测视角

✅ 已完成

本课要解决什么

不要把 RWX 当作唯一注入规则。检测要把模块、内存区域、线程入口和行为历史组合成证据链，区分可疑现象与更可靠的执行证据。

30 秒核心结论

私有可执行内存本身只是线索；线程从其中启动才是强执行证据。没有 RWX 也不能证明安全，因为载荷可先写入 RW 内存，再改为 RX 后执行。

DEP / ASLR / CFG 各自限制什么

机制限制对象对注入或控制流攻击的意义
DEP数据页能否执行阻止把普通 RW 数据页直接当机器码运行；攻击者仍可能申请或改成可执行页。
ASLR模块加载地址的可预测性让硬编码函数地址、固定 gadget 或部分 ROP 链不可靠；运行时泄露或解析实际地址后仍可能绕过。
CFG间接调用/跳转的合法目标限制控制流跳到未允许的目标地址；它不负责检测所有注入，而是增加任意跳转的难度。

检测证据链

可疑私有内存出现
  -> 写入载荷（若能观测）
  -> RW 改为 RX/RWX（若能观测）
  -> 线程从该地址启动，或控制流进入该地址
  -> 结合进程句柄、模块和调用上下文定性
观察说明误区
RWX 内存可写后立即执行，值得关注JIT、调试器等正常组件也可能使用，不能单独定性。
MEM_PRIVATE + RX不属于普通已加载映像模块的可执行区域只能说明来源值得核查，尚不等于攻击。
线程起始地址落入该区域该私有内存实际承担了执行入口这是强信号，仍应结合进程用途和时间线排除误报。

反注入思路

典型远程线程链是：获取目标进程高危句柄 -> 写入内存 -> 修改执行权限 -> 创建或劫持线程。防守应优先控制前端的高权限句柄，遵循最小权限原则，并监控写内存、改保护属性和创建线程等组合行为。单独的只读进程内存权限常用于诊断或扫描，不能据此直接定性。

尚未实测：本课未运行实时进程枚举、内存权限监控或调试器验证，因此没有把推理结论写成特定进程的实测结果。

常见误区

“没看到 RWX 就安全”是错误结论。先写 RW、再改 RX 的载荷在最终快照中可能只留下 RX；检测应尽量结合权限变化历史和线程执行位置。

Day 11 — x64 汇编 + IAT Hook

✅ 已完成   最小实验：自己 Hook 自己进程的 MessageBoxA

本课要解决什么

写一个能真正生效的 IAT Hook，并且用调试器证明执行链：调用被拦截 → 先进 Hook 函数 → 再调回原函数。前提是先吃透 Windows x64 调用约定——参数怎么传、栈怎么摆。

30 秒核心结论

IAT 槽位是存函数地址的 8 字节格子；IAT Hook = 把目标函数槽位里的地址换成自己函数的地址。程序执行 call [IAT槽位] 时照着格子里的地址跳，于是跳进 Hook 函数。Hook 函数想恢复原行为，必须先保存原地址，再通过保存的指针调用原函数。

x64 调用约定（四条规则）

规则内容意义
1前 4 个整数/指针参数 → RCX、RDX、R8、R9参数不压栈，直接放寄存器
2浮点参数 → XMM0-XMM3（整数浮点各自独立编号）游戏坐标等 float 参数在 XMM 里
3调用任何函数前，RSP 必须 16 字节对齐API 内部用 SSE 指令，SSE 要求 16 对齐，不对齐一进 API 就崩
4调用方预留 32 字节影子空间（Shadow Space）被调函数存放 RCX/RDX/R8/R9 的临时区

崩在别人家，错在自己家：RSP 对齐是“调用那一刻”由调用方保证的；崩溃点常在 API 内部，原因却在调用方没对齐。

INT vs IAT（导入表两列）

装什么比喻
INT（OriginalFirstThunk）函数名字购物清单
IAT（FirstThunk）函数真实地址收货地址

INT 和 IAT 里的函数按同一顺序排列：在 INT 里找到目标函数名，记下标，到 IAT 同下标取槽位。

IAT Hook 执行链

1. 找到目标函数在 IAT 里的槽位（PE头 → 导入表 → 目标DLL → 按名字匹配）
2. 保存槽位原值（原函数真实地址）到全局变量
3. VirtualProtect 把槽位所在页改成可写
4. 把槽位里的地址替换成 Hook 函数地址，再恢复页属性
5. 程序再调用该函数 → call [IAT槽位] → 跳进 Hook 函数
6. Hook 函数干完自己的事 → 通过保存的原地址调用原函数

常见误区

  • “Hook 是替代原函数” ❌ —— 是插队加活，默认要调回原函数，否则程序功能被破坏（该弹的窗不弹本身就是最大破绽）。
  • “附加进程 = 注入” ❌ —— 附加进程是调试器挂到已运行进程，注入是把代码塞进别的进程，两回事。
  • “IAT 槽位是函数名” ❌ —— 槽位存的是地址，名字在 INT 里。

防御视角

IAT Hook 不改代码，只改数据（IAT 页）。检测侧可校验导入表完整性：比较磁盘上的 IAT 原值与内存中的当前值，或检查 IAT 页是否被写保护篡改过（VirtualProtect 留下的权限变化痕迹）。它是静态替换，容易被完整性扫描发现，属于低隐蔽性 Hook。

Day 12 — Inline Hook

✅ 已完成   最小实验：x64 self-hook + x64dbg

复习入口

已确认：把 Target 开头换成一张跳转牌：执行路线改去 HookAdd，但 RCX/RDX 里的参数 3/5 不变；被覆盖的原指令先放进 trampoline，Hook 处理完再接着执行。

不要混淆：Inline Hook 不是固定写 5 个字节：E9 只需要 5 字节，但被覆盖的范围必须在完整指令边界结束；x64dbg 先停在 ntdll 或 mainCRTStartup 也只是启动过程，不算 Hook 命中。

下一步：Day 13 VTable Hook：把函数入口改跳转，和把对象的虚函数表槽位换地址进行对比。

本课要解决什么

Inline Hook 要解决的是：目标函数已经在程序里，怎样在它一进门时把执行路线引到自己的 Hook，同时保留原来的行为。大白话：不把整栋房子换掉，只在 Target 门口放一块指路牌，告诉 CPU 先去 HookAdd。

30 秒核心结论

Inline Hook = 改目标函数开头的机器码。本实验把 Target 开头的完整指令复制到 trampoline，再把 Target 开头改成 5 字节 E9 rel32 跳转，并用 NOP 补齐到 8 字节。Target 被调用时先跳到 HookAdd；Hook 处理完通过 trampoline 执行被覆盖的原指令，再跳回 Target+8。

前置知识

需要知道 x64 下整数参数前四个通常在 RCX、RDX、R8、R9；知道机器指令不是固定长度；知道函数入口的字节可以被调试器和程序读取。这里的最小实验是自钩取（self-hook），不涉及跨进程注入。

执行链

1. 读取 Target 开头的原始字节
2. 只选择完整指令，复制到附近的 trampoline
3. trampoline 执行原始字节，然后跳回 Target+8
4. 把 Target 开头改成 E9 rel32 + NOP
5. main 调用 Target(3, 5)
6. CPU 从 Target 开头跳到 HookAdd，RCX=3、RDX=5 保持不变
7. HookAddBody 打印命中，再调用 trampoline
8. trampoline 执行原逻辑并回到 Target+8，最后返回 18

本实验的关键字节

位置实测字节含义
Before8B C1 03 C2 FF C0 8B C84 条完整的 2 字节指令
PatchedE9 0B 00 00 00 90 90 905 字节相对跳转 + 3 个 NOP

这里选择 8 字节不是因为 Inline Hook 永远必须覆盖 8 字节，而是因为本实验的 Target 入口刚好能用 8 字节容纳完整指令，并且代码用一次 8 字节写入完成补丁。

已验证 vs 仅为推测

已验证：入口字节发生 E9 detour；Target(3,5) 进入 HookAdd；Hook 停点的 RCX/RDX 是 3/5；trampoline 让结果仍为 18；恢复字节后 Target 仍返回 18。

仅为推测或未单独压力测试：多线程同时执行 Target 时，单次 8 字节原子写入能降低读到半截补丁的风险，但本实验没有做并发压力测试，不能据此宣称完整线程安全。真实 Hook 还要审核正在执行的线程、指令缓存刷新和 trampoline 的可达距离。

失败实验与误区

  • 把 5 字节当成固定覆盖长度：E9 本身是 5 字节，但如果前一条指令 2 字节、下一条指令 4 字节，只覆盖前 5 字节就会把第二条指令切开；CPU 之后读到的字节会错位，可能异常、崩溃或跑出错误结果。
  • 把 ntdll 停点当成 Hook 命中：x64dbg 启动目标时可能先停在 Windows 的系统加载代码或 mainCRTStartup。截图没有显示自己的 HookAdd，就不能算实验命中；这次通过清理入口停点并使用明确的 HookAdd 停点解决。
  • 只跳进 Hook 不回原函数：如果 HookAdd 做完自己的事就返回，原来的加法逻辑可能完全不执行；trampoline 的作用就是把被覆盖的原代码接回来。

逆向与防御视角

分析者看到函数入口突然出现 E9、FF 25 或其他长跳转时，应先保存原始字节，确认跳转目标，再判断是否存在 trampoline。防御侧可以比较磁盘镜像和内存中的代码入口，检查 VirtualProtect 后的代码页权限变化、私有可执行 trampoline、指令缓存刷新和线程同步风险。Inline Hook 直接改代码，通常比只换 IAT 槽位更容易在代码完整性检查中留下痕迹。

Day 13 — VTable Hook

✅ 已完成

复习入口

已确认：把当前对象的 vptr 换到一张可写的 vtable 副本，再把副本的 slot 0 改成 HookAdd；虚调用先进入 HookAdd，HookAdd 用保存的原始 Add 完成原逻辑，最后恢复原 vptr。

不要混淆：保存原函数地址是为了让 HookAdd 还能调用原 Add；复制 vtable 是为了隔离对象。直接改公共 vtable 会影响所有共享它的对象，原表只读时写入还可能崩溃。

下一步：Day 14 VEH Hook + SEH 对比：从函数表替换转到异常分发和异常入口。

本课要解决什么

VTable Hook 要解决的是：不改函数入口机器码，只改某个 C++ 对象通过虚函数表找到函数的路线。大白话：对象手里有一张“函数地址表”，这次只给当前对象换一张副本，把 Add 对应的格子换成 HookAdd。

30 秒核心结论

VTable Hook = 替换对象的 vptr 指向的虚函数表槽位。对象的第一个指针通常是 vptr，它指向 vtable；本实验复制原表的两个槽位，把副本 slot 0 改成 HookAdd，再把当前对象的 vptr 换到副本。原始公共 vtable 不动，其他对象不跟着改变。

Calculator 对象开头
+0x00  vptr  ──>  vtable 副本
                         [0] ──> HookAdd
                         [1] ──> Calculator::Multiply

g_originalAdd 保存的是原来的 Add 函数地址，作用是让 HookAdd 还能执行原逻辑；复制 vtable 和改 vptr 的作用是只改变当前对象的虚调用路线。这是两件不同的事。

执行链

1. 原来：对象 vptr 指向原始 vtable，slot 0 是 Add
2. 复制原始 vtable 的两个指针到可写副本
3. 保存副本 slot 0 中的原 Add 地址
4. 把副本 slot 0 改成 HookAdd
5. 把当前对象的 vptr 改成副本地址
6. InvokeAdd(object, 3, 5) 按虚调用查表，先进入 HookAdd
7. HookAdd 调用保存的原 Add，得到 8，再加实验用的 100，返回 108
8. InvokeMultiply 仍走 slot 1，结果保持 15
9. 实验结束把原 vptr 写回，释放副本，Add 恢复为 8

失败实验与排查

  • 把自带 __debugbreak() 当作教学断点：程序会在调试异常和下一条 int3 之间来回切换，反复按 F9 也不能稳定得到普通断点证据。修复方式是移除自带 INT3，改用 x64dbg 在符号 HookAdd 上设置普通 F2 断点。
  • 直接改原始公共 vtable：所有共用这张表的对象都可能一起被 Hook；而且原表常常位于只读区域，写入可能触发访问冲突。副本加对象级 vptr 是更容易隔离和恢复的教学方案。
  • 把 HookAdd 当成原 Add：如果不保存原函数地址，Hook 只能截断原逻辑；g_originalAdd 让 HookAdd 能在记录或修改行为后继续调用原 Add。
  • 只凭一个绝对地址判断：ASLR 会改变模块基址和函数地址，应该结合模块、符号、RIP、寄存器和内存内容一起确认。

本课要解决什么

Day 11-13 都是在“改路”：换 IAT 地址、改函数入口、换虚表槽位。Day 14 改成“站岗”：不改目标函数机器码，而是在当前进程的异常分发链上注册一个 VEH（Vectored Exception Handler，向量化异常处理器），观察它怎样先于局部 SEH（Structured Exception Handling，结构化异常处理）收到异常，并决定自己接管还是继续往下找。

30 秒核心结论

本实验的简化分发顺序是：调试器 first-chance -> 进程级 VEH -> 栈帧关联的 SEH -> 调试器 second-chance -> 未处理异常终止。E0421401 在 Day14VehHandler 返回 EXCEPTION_CONTINUE_EXECUTION，搜索停止，结果从 8 变成 108；E0421402 在 VEH 返回 EXCEPTION_CONTINUE_SEARCH，随后进入 SehFilter，由 __except 处理并得到 200。

实验模型与边界

这里的“VEH Hook”是可验证的最小教学模型：VehHookTarget 主动调用 RaiseException，VEH 通过进程内共享状态改写结果，然后让执行继续。代码没有修补目标函数入口，也没有把它包装成可直接套用到任意函数的通用 Hook；真实异常型 Hook 还可能修改 CONTEXT、配合页保护或硬件异常，本课没有覆盖这些路线。

执行链和前提

0. AddVectoredExceptionHandler(1, Day14VehHandler) 在当前进程注册 VEH

路径 A：E0421401
VehHookTarget(3,5) 保存原结果 8
  -> RaiseException(E0421401)
  -> 调试器 first-chance（有调试器时）
  -> Day14VehHandler 读到 E0421401
  -> 写入 hooked=108，返回 CONTINUE_EXECUTION
  -> RaiseException 后继续，VehHookTarget 返回 108

路径 B：E0421402
RunSehFallbackPath 的 __try 调用 SehFallbackTarget
  -> RaiseException(E0421402)
  -> Day14VehHandler 先记录 VEH declined，返回 CONTINUE_SEARCH
  -> x64 表驱动异常搜索定位到这一帧的语言处理器
  -> SehFilter(E0421402) 返回 EXCEPTION_EXECUTE_HANDLER
  -> __except 块把结果设为 200

结束：RemoveVectoredExceptionHandler 注销 VEH

AddVectoredExceptionHandler 的第一个参数为非零，表示把它放到当时 VEH 列表的最前面；如果后续又有处理器以 first 方式注册，顺序仍可能变化。“全局”只表示当前进程内不依附某个栈帧，不是全系统共享。

x64 表驱动异常：本机二进制证据

dumpbin /headers 确认 Debug 产物是 PE32+ x64，Exception Directory 为 RVA 0x9000 / size 0x564，最终映像的 .pdata 节位于 RVA 0x9000 且为只读。dumpbin /unwindinfo 能看到 Day14VehHandler 的函数表项、SehFilter 起点 0x1400，以及包含 __try/__except 的函数使用 __C_specific_handler 和 scope table。

Microsoft 文档把这套静态数据称为 pdata 指向 xdata。当前最终 Debug EXE 没有单独命名的 .xdata 节；函数表中的 unwind 信息 RVA 落在只读 .rdata，说明链接器把相应贡献合并了。文章因此区分“架构术语中的 xdata”和“这个最终 PE 的实际节名”。x64 通过当前 RIP 查 RUNTIME_FUNCTION/UNWIND_INFO，不再依赖 x86 经典的栈上异常登记链；这移除了经典 SEH 链覆盖这一攻击面，但不等于整个栈不可篡改，也不等于所有异常元数据永远静态不变，JIT 等动态代码可以注册函数表。

  • E0421401 和 E0421402 都先进入本进程注册的 VEH；前者在 VEH 结束搜索，后者由 VEH 放行后进入 SEH filter。
  • Debug/Release 单项目构建和独立运行均成功，两条路径分别稳定返回 108 与 200。
  • 普通 x64dbg 已取得 handler 中两个异常码以及 SehFilter 的 RIP/RCX 证据；本轮源码、RVA、反汇编和 unwind 元数据相互一致。
  • C0000005 是真实访问违例代码，但不是本实验主动抛出的两个目标异常。

仅为推测或仍未验证

  • 普通 x64dbg GUI 从嵌套异常处理者的软件断点人工续跑时出现 C0000005，差异已限定在该交互场景；没有证据定位 x64dbg 内部的精确故障点，也不把它写成调试器缺陷的已确认根因。
  • x64 表驱动设计降低经典栈上 SEH 链覆盖风险是架构结论；本课没有搭建攻击样本做利用对比，不能据此宣称“x64 上所有异常利用都被杜绝”。
  • 本实验验证的是主动 RaiseException 的教学路径，不代表所有硬件故障都适合返回 CONTINUE_EXECUTION；若没有修复触发故障的上下文，继续执行可能立刻再次异常。

失败实验与稳定替代路线

  • 普通 GUI 人工续跑：干净 x64dbg GUI 能进入 Day14VehHandler，但在 handler 软件断点内按 F9/Shift+F9 后，历史会话于同一 ntdll!00007FFE7336C286 重复出现 C0000005，handler 断点也曾不命中。隔离 headless 脚本控制同一目标能从 E0421401 继续到 E0421402，而独立运行始终 PASS，因此已验证目标代码和 Windows VEH 返回链可用；未验证的是 GUI 人工续跑交互的内部根因。
  • 稳定路线：每个证据点使用新进程和一次性自动检查点，到目标就停，不再做第三次同类人工续跑。这样分别取得两个 handler 异常码和 SehFilter 的 RIP/RCX。
  • 符号断点：bp day14vehhook.Day14VehHandler 曾提示无效地址；改用当前模块基址加 Debug RVA 0x1240 后断点被接受。绝对地址受 ASLR 影响，不能跨进程照抄。
